# THE ENTIRE PRODUCT (phone-scan -> parametric CAD pipeline)
VERDICT: DESCOPE

THE KILL CASE, at full strength. (1) The only differentiation this product could claim over Backflip/Paramesh is precision — the mating-fit gap — and the metrology evidence says the sensors cannot deliver it, period: LiDAR ±10mm with a ~5cm feature floor and ML-hallucinated depth between ~576 real points; TrueDepth 1.8-4.5mm flatness error and +1.76mm diameter bias; ARKit drift 20-40mm/s. The one path to sub-mm (photogrammetry ±0.1-0.5mm) is UNVERIFIED on smartphones, threatened by OIS/AF intrinsics instability, and its scaling step (ChArUco) has no benchmarked implementation anywhere on earth. 'Nobody ships press-fit tolerances from phone capture' is not a market gap — it is a physics verdict. A $30 caliper delivers ±0.02mm, three orders of magnitude better than anything this pipeline will ever emit. (2) Even granting good points, no 2024-2026 method turns primitive soup into watertight B-rep on real scans (HoLa 82-84% on SYNTHETIC; Point2CAD license-dead; ComplexGen dependency-dead), and tonight's CGAL 0.13% cylinder result required synthetic 0.1mm-noise data with oriented normals the evidence base itself says real scans won't have. (3) The capture stack cannot even be worked on tonight: LeapDepth's AVCaptureSession is mutually exclusive with ARKit, no app pairs 12MP stills with poses, and the phone is untouchable until morning — so any iOS work is unverifiable speculation. (4) The decisive local evidence: the user's own build_enclosure.py in this directory is already the 'output' this product promises — a named-dimension parametric script — and its critical dimensions came from DATASHEETS (APIELE 16mm button spec, uxcell 42mm mount spacing, USB-C standard cutout), not from measuring, let alone scanning. For the user's actual work (ESP32 enclosures around known components), scan-derived geometry is strictly worse input than the spec sheets already in use. On this evidence, the honest recommendation is: cancel the scan-to-CAD dream, keep writing scripts from datasheets and calipers, go to bed. WHAT DEFEATS IT — narrowly, and only in one place: accessibility. Backflip is a Fusion add-in and a visual web app; Paramesh emits opaque STEP; Polycam/KIRI emit meshes for visual editors. Every incumbent, paid or free, terminates in an artifact this user cannot read. 'Scan with an existing app and feed Backflip' fails not on price but on output modality: a blind user cannot review Backflip's feature tree for the small-critical-feature errors reviewers report it making — silent wrong geometry is worse than no tool. And there is one task the datasheet+caliper incumbent genuinely cannot do for this user specifically: perceiving the shape of an unknown or non-prismatic object — where is the boss relative to the edge on this bracket, what is the curvature of this housing — which sighted makers solve by looking. A pipeline that turns a commodity mesh into a plain-text geometry report and a build123d script with named, uncertainty-tagged dimensions is not a Backflip competitor; it is perception tooling, and nobody ships it. That defeats the total kill — but it kills 80% of the product with it: the moment you accept 'scan values are ±1-10mm drafts, calipers/datasheets are truth,' the entire precision stack (iOS capture app, ARKit poses, COLMAP/GLOMAP, ChArUco mats, photogrammetry validation) becomes unnecessary, because coarse metric meshes already fall out of free tools (Apple PhotogrammetrySession, Stray Scanner) the user can run in the morning.

SURVIVES: A Mac-side CLI on the already-verified stack (open3d 0.19 + CGAL 6.0.1 Efficient RANSAC + build123d 0.11.1): mesh in -> spoken/plain-text geometry report (primitives, dimensions, relative positions) + a build123d script skeleton with NAMED dimensions, each tagged with scan-derived uncertainty and meant to be overwritten by caliper/datasheet values -> STEP out (gencad/FreeCAD 1.1.3 as fallback emitter). One sentence of what the product IS: a screen-reader-native describe-and-draft tool that turns any phone-scanned mesh into a plain-language geometry report and an editable named-dimension CAD script, where the scan is the draft and the caliper is the truth.

TONIGHT: BUILD: the mesh->report+script CLI end to end on the verified local stack — including the CGAL RANSAC param-string parser (with unit tests) and normal-estimation preprocessing — validated tonight against synthetic meshes PLUS degraded variants (added noise, corrupted/unoriented normals, holes) that mimic real-scan quality per the metrology data; emit both the text report and a compiling build123d->STEP script for each test case. SKIP: all iOS work, LPD1/LeapDepth extension, COLMAP install, ChArUco anything, and every precision/tolerance claim. STUB: capture, as a one-page morning protocol — scan with Apple PhotogrammetrySession or Stray Scanner (both free, metric), drop the mesh on the CLI. Decision report states plainly: this tool never competes with Backflip on accuracy; it competes with silence.

DECISIONS:
- Two-channel accuracy model adopted: scan-derived dimensions are coarse drafts (±1-10mm, always uncertainty-tagged); calipers and datasheets are the only trusted channel — the pipeline therefore never needs, and never claims, sub-mm accuracy.
- Kill the custom capture stack: input is any commodity metric mesh (Apple PhotogrammetrySession preferred, Stray Scanner fallback); the LeapDepth/ARKit coexistence problem and the 12MP+poses gap become someone else's problem.
- Kill the precision research track: no COLMAP install, no ChArUco scaling (no benchmarked implementation exists), no smartphone-photogrammetry validation — all made unnecessary by the two-channel model.
- Primary CAD emitter is build123d 0.11.1 (verified STEP output, cleaner scripts for screen-reader editing); gencad MCP bridge / FreeCAD 1.1.3 headless retained as fallback — consistent with the user's existing FreeCAD scripting workflow.
- Synthetic validation must include degraded meshes (noise, bad/unoriented normals, holes), because the CGAL 0.13% result was achieved under lab conditions the evidence base says real scans will not meet.
- Product identity fixed as accessibility perception tooling, not reverse-engineering CAD — which is why Backflip ($20/mo, visual GUI, reviewer-reported silent feature errors) and Paramesh (opaque STEP, 3% volume error) are not substitutes for this user.
- No commercial framing: personal-tool economics only; success metric is whether the morning scan of one real object yields a report+script the user can act on.

# LiDAR/TSDF fusion leg (Stray Scanner capture -> confidence filtering -> Open3D TSDF -> fused cloud for primitive fitting)
VERDICT: KILL

Confidence filtering filters on the ML model's confidence in its own hallucination — it removes the honest holes and keeps the confident fabrications. Feeding this to CGAL Efficient RANSAC — which per tonight's smoke test needs oriented normals and already degrades badly on real-scan normals — produces primitives with clean parameter strings and 10mm-biased dimensions. A script that prints 'boss_diameter = 6.3' derived from hallucinated geometry is strictly worse than no number: the incumbent (caliper + typed dimension) is accurate to 0.02mm and fully available to this user today. Coarse context topology: Apple PhotogrammetrySession already returns a free metric-scaled mesh from HEIC+depth+gravity with zero adapter code — no Stray Scanner ingest, no ffmpeg HEVC extraction, no 192x256 confidence plumbing, no voxel/sdf-trunc tuning. The kill case stands: the TSDF fusion leg is dominated in every role, poisonous in its main role, and untestable tonight.

# B-Rep middle (primitive segmentation -> constraint inference -> automated solid assembly)
VERDICT: DESCOPE

THE KILL CASE. (1) The intersect/trim/sew step is a research problem, not an engineering task. The evidence base is unambiguous: no 2024-2026 paper-with-code solves primitive-soup -> watertight B-rep on real scans. Worse, 'constraint inference' at this noise level is vacuous: you cannot statistically distinguish 'designed parallel' from 'measured 2 degrees off' when angular uncertainty from the sensor swamps the design intent — so any inference engine degenerates into threshold snapping, which needs ~50 lines, not a solver. (3) Backflip AI GA'd sixteen days ago at $20/mo selling exactly the automated middle — scan -> parametric CAD with feature trees — and reviewers already show it missing knob notches and thin walls with zero tolerance claims. The user typing one `extrude(profile, amount=box_height)` line costs less than the trust deficit of any Boolean op we could ship untested. (5) Nothing physical can happen tonight — no captures, no prints, no calipers — so any assembly automation would be validated purely on synthetic clouds and shipped blind against real scans whose normals the evidence base already flags as 'much worse.' WHAT DEFEATS TOTAL KILL: the middle cannot go to zero. CGAL Efficient RANSAC is the one verified-working precision asset (12.5mm cylinder to 0.13% synthetic), build123d -> STEP works, and a raw CGAL parameter string is not a product — for a blind user it is exactly the fit -> named-dimension -> script step that converts a point cloud into something usable at all, since eyeballing a mesh for dimensions is not available to them. So the component survives only as: fit primitives, snap to a dominant frame with reported (never silent) snapping, emit a script skeleton. Everything past that — constraint graphs, trimming, sewing, automated Booleans — dies.

SURVIVES: A ~3-stage 'thin middle': (a) CGAL Efficient RANSAC fitting of planes + cylinders only, with param-string parsing and per-primitive RMS residual + inlier count; (b) dominant-axes frame extraction (cluster plane normals, pick orthogonal triad) with snap-to-frame plus concentric/equal-radius merging by tolerance clustering — no pairwise constraint-graph solving; (c) emission via build123d of a script SKELETON: datum planes/axes, named dimensions (box_width = 42.3  # fitted 42.31, RMS 0.4mm), commented assembly hints ('# plane_top parallel plane_bottom, gap 24.85 -> height=25.0?'), and NO executed Boolean/extrude operations. Every snap reports raw fitted value, snapped value, and deviation in the emitted script — silent snapping is lying about data. The gencad/FreeCAD STEP path stays as the downstream once the user completes the script.

TONIGHT: BUILD: single CLI `cloud2skeleton.py` — point cloud in, build123d skeleton script out — planes+cylinders only, dominant-frame snapping with defaults derived from the metrology numbers (angular snap 5 deg / dimensional snap 2x RMS residual for the LiDAR regime; 1 deg / 0.5mm for the TrueDepth regime, both overridable flags), every snap and residual reported as comments in the emitted script. TEST: synthetic-only harness (constraints forbid captures) — generate >=3 known-ground-truth prismatic+cylindrical clouds at 0.5mm and 10mm noise, assert emitted named dimensions within stated tolerance and that the skeleton executes under build123d 0.11.1 to valid datums. SKIP: cones/spheres/torus, pairwise parallel/perpendicular constraint inference, and ALL automated solid assembly including extrude-between-parallel-planes — the latter appears only as a commented suggestion, not code. STUB: nothing — a stubbed sewing stage would signal intent to build it later; do not create the file.

DECISIONS:
- Primitives tonight: planes + cylinders only — matches enclosure/prismatic maker parts, and real-scan normal quality (flagged 'much worse' in evidence) makes higher-order quadrics fit-to-noise
- Constraints worth code: dominant-orthogonal-frame snapping + concentric/equal-radius clustering only; pairwise parallel/perpendicular constraint-graph solving is killed (that is the road that led ComplexGen to Gurobi+Mosek)
- Snapping tolerances are derived, not magic: threshold = f(per-primitive RMS residual, sensor regime), defaults 5deg/2xRMS for LiDAR (+-10mm evidence), 1deg/0.5mm for TrueDepth (0.27-0.79mm noise evidence), all overridable and all reported
- No silent snapping ever: emitted script carries raw fitted value, snapped value, and deviation as a comment on every named dimension
- Automated solid assembly killed tonight AND at product scope in its general form; the only future candidate is extrude-between-parallel-planes behind an explicit user confirmation, and tonight it ships only as a commented hint in the skeleton
- Human is the topology engine by design, not by deficiency: for a blind script-first user the editable skeleton with named dims is MORE accessible than any automated mesh-to-solid output, so automating assembly adds risk while subtracting the product's differentiator
- Validation regime tonight is synthetic ground truth only, per the hard constraint that no physical capture/measurement is possible before morning
